# 音乐查询与分页

音乐联想保留歌曲、歌手和专辑的原有排序、响应与数量限制。同一次请求中，最多八首候选歌曲先按歌手和专辑 ID 去重再查询关联记录，避免同专辑歌曲反复点查；按候选首次出现顺序合并直接命中，不保留跨请求缓存。

直接命中的最多五张专辑，以及候选歌曲关联的专辑，复用普通列表的九字段投影与旧库缺列回退。联想卡片省去未使用的简介和来源路径读取；歌曲选择、歌手查询、直接匹配、合并顺序、拼音回退与公开数量限制保持，专辑详情仍返回完整简介。

正常表结构的私有样本中，八张关联专辑和五张直接命中专辑各有 512 KiB 简介时，冷、暖联想请求的简介读取均从 6.5 MiB 减至零，语句准备与执行次数保持。零简介、8 KiB 简介、重复关联、缺项、旧列类型与缺列回退另有完整响应、SQL 参数及查询计划对照；旧库回退仍读取简介，不承诺所有资料分布都更快。

## 歌词分页

歌词搜索只返回 `music_tracks.status = 'ok'` 的有效曲目。短词使用原有 LIKE 匹配，在 LIMIT/OFFSET 前核对曲目有效性；总数也按相同条件计算。失效或孤立歌词不会占满一页，客户端可继续读取后面的有效结果。

短词的一页通过一条关联查询取得曲目、歌手、专辑和个人播放状态，取消逐首曲目的重复点查。候选歌词沿用原有扫描顺序，不引入名称排序；SQL 没有声明全局固定顺序，跨请求资料变化仍可能改变分页。

至少三个非空白字符沿用 FTS 匹配与相关度、播放次数和名称排序。FTS 总数同时核对有效曲目及歌词记录，避免孤立或失效的搜索索引把 `total` 和 `hasMore` 抬高。歌词上下文、高亮、查询规范化及响应字段保持原有规则。

## 智能歌单计数

最近播放、常听、收藏、高分和重温歌单必须有个人状态记录。详情页的总数从状态表关联有效歌曲计算，避免每页扫描全部歌曲再逐条查状态；缺失歌曲和孤立状态仍不计入。歌单条目查询、排序、分页和其他歌单计数保持原有规则，未听与待评分仍包含没有状态记录的歌曲。

重温歌单在同一次请求中只计算一次时间边界，计数与条目复用同一条件。不添加跨请求缓存，也不把其他歌单的汇总元数据作为详情页的即时总数。

智能歌单索引在本次请求内合并六项状态计数，共享一次状态与有效歌曲关联；未听、待评分共享原有效歌手的歌曲总数并保留零下限。候选行沿原完整谓词筛选，不把旧文本、空值或孤立状态当成新的有效记录。重温计数仍在歌单顺序的原位置单独计算时间边界；静态计数元数据及其缺失回退、单个歌单详情沿用原流程。

正常静态计数与热汇总下，状态 SQL 从七条减为两条，歌手总数聚合从两条减为一条。10 万首曲目的密集私有样本中，完整请求中位耗时约从 122 ms 降至 54 ms；空状态和大量无播放、收藏或评分状态也核对原结果与关联次数。计数随每次请求读取，不添加跨请求状态缓存；诊断计时不代表真实资料库延迟。

## 歌手分页缓存

没有搜索词、按名称排序的歌手列表，在原 `SELECT *` 之后只保留响应需要的七个原始字段，继续按原名称规则排序。每页再生成独立响应对象；不提前转换所有歌手的值，不把缓存对象交给调用者。保留全列查询以兼容缺少可选计数列的旧库，搜索路径沿用原处理。

缓存仍按现有筛选键和数据库连接归属保留，沿用原 LRU、单项 4 MiB 及总容量上限、扫描失效和关闭规则。20,000 名合成歌手中，19,795 条匹配记录的估算 JSON 权重从 12,035,587 字节降至 2,454,488 字节；原结果超过单项上限而不保留，新结果可保留。随后十二页的全量读取从十二次降至零，重复排序的行数从 237,540 行降至零；冷查询仍读取全部匹配记录，权重也不是实际堆内存测量。

## 专辑计数

普通专辑列表及只按歌手 ID、曲风或标题首字母筛选的总数，不再逐张关联歌手表。搜索可能匹配歌手名称，语种来自歌手记录，“待”筛选也依赖歌手名称，因此这三种条件仍保留原关联。

分页行继续关联歌手，返回原有名称、匹配标记、排序和分页字段。零曲目或失效歌手、缺失歌手的专辑仍按原计数规则处理；曲风筛选仍只根据有效曲目。初始化和旧列迁移流程保持原样。

私有专辑样本通过完整旧响应对照和实际计数查询计划检查，普通总数的 20,000 次歌手主键查找减为零；计数仍执行一次 SQL，不添加缓存或索引。

## 专辑列表字段

专辑筛选项只读取公开列表需要的九个专辑字段及歌手名称，省去简介、简介路径和来源路径等未使用字段。最多六十项的关联、筛选、排序和缓存键沿用原 SQL；选中的专辑不在前六十项时，补查也采用相同字段。专辑详情继续读取并返回完整简介与来源信息。

部分旧专辑表缺少年份、封面、时长、大小或更新时间列。仅在准备语句时报出这些新增投影列的原生缺列错误时，回退为原来的完整字段查询；其他准备或执行错误继续向上传递。不额外查询表结构或保存兼容性状态，旧库回退仍读取简介，每条需要回退的查询增加一次失败的语句准备。

使用正常表结构的私有完整歌单样本中，六十张专辑各有 512 KiB 合法简介时，筛选读取到 JavaScript 的简介字节从 30 MiB 减至零；SQL 执行次数与查询计划保持，完整响应与旧实现一致。缓存命中、扫描发布、关闭与重开、旧列类型及缺列回退另有对照；本机计时只作诊断。

普通专辑分页复用同一字段投影和旧库回退，总数、筛选、关联、排序、offset 与公开映射保持。每张有 512 KiB 简介的正常表样本中，默认八十项页的简介读取从 40 MiB 减至零，三百项页从 150 MiB 减至零；完整冷请求仍执行九条 SQL，暖分页仍执行两条。零简介及 8 KiB 简介、并列与空值、搜索组合、末页和原错误另有完整响应与实际查询计划对照；详情不采用此投影。

## 播放最多汇总

`summary().topPlayed` 先按原播放次数、最近播放时间和标题规则选出最多八首歌曲，再关联歌手名称、专辑名称及封面。排序仍从个人状态关联歌曲，缺失歌曲的状态不会占用名额；完整并列时保留原选入项和顺序。

歌手与专辑关联仍在同一条 SQL 中读取，不增加跨查询快照。缺少关联记录时保留原展示回退，进度、状态时长和评分字段也保持原映射；不增加曲目有效性条件。汇总继续按既有五秒有效期、状态变化及扫描发布刷新。

私有 10,000 首曲目样本中，符合播放条件的 9,604 行原本逐条关联歌手和专辑，现在每类仅关联最终八行。完整冷汇总的 SQL 次数保持；计时只作诊断，不代表实际资料库延迟。

## 验证

```powershell
npm run verify:music-lyric-search
npm run verify:music-summary-cache
npm run verify:music-facet-cache
```

验证使用当前 store、实际 schema 与扫描发布、私有 SQLite 和合成曲目及歌词，核对完整旧响应、关联查询次数、失效曲目分页、计数一致性和后续请求更新。联想覆盖关联去重、专辑字段投影与旧库回退、匹配及合并顺序、错误和下一请求更新；恢复旧联想完整字段应超过简介读取预算，原关联点查负控继续触发查询次数断言。智能歌单覆盖密集及稀疏状态、旧列类型、静态元数据回退、计数合并、分页和时间边界；旧索引计数负控应超过状态查询与关联预算。歌手覆盖缓存权重、分页复用、旧列与空主键、返回隔离、失败重试及连接归属，恢复旧宽记录构建应在分页读取预算处失败。专辑覆盖搜索、语种和字母组合、歌手缺项、旧列迁移与缺列回退、普通分页与筛选补查；默认和最大页核对完整旧响应、SQL 参数及查询计划，分别恢复旧分页或筛选完整字段均应超过简介读取字节预算，详情简介保持完整。播放汇总覆盖完整并列、缺失关联、状态时长回退、旧列迁移及关联查找门槛，继续验证缓存命中、写入与扫描失效。歌词检查已纳入 `verify:music-scale`；不读取真实音频、歌词或资料库，本机 fixture 不代表正式服务已部署。
